# Bufy fork of the Mattermost desktop app

Fork of [mattermost/desktop](https://github.com/mattermost/desktop) (Apache-2.0), branch `bufy/main`, based on upstream tag **v6.4.0** (Electron 45.2.1).
It adds a small, safe API for our own Mattermost plugins (Voice Rooms, Calls fork) under `window.desktopAPI.bufy`, and a
reproducible way to build unsigned packages ([BUILD.md](BUILD.md)).

All fork code lives in **`src/main/bufy/`**. Everything else is a minimal hook into upstream files (listed below, each
marked `[bufy]` in the source so `git grep "\[bufy\]"` finds every one).

## API

Types: [`desktop-api-bufy.d.ts`](desktop-api-bufy.d.ts) (generated by `node scripts/bufy-gen-types.js` from `src/main/bufy/shared.ts`).

`window.desktopAPI.bufy` only exists in this fork. **Feature-detect it**; plugins keep working on the stock app:

```ts
const bufy = (window as any).desktopAPI?.bufy;   // undefined on the stock app
bufy?.version;                                   // '1.2.0'
```

Every method returns a promise that resolves to `{ok: true, ...}` or `{ok: false, error, message?}`. Nothing rejects. Error codes:
`untrusted-sender`, `invalid-argument`, `rate-limited`, `unsupported`, `permission-denied`, `source-not-found`, `in-use`,
`limit-reached`, `registration-failed`, `timeout`, `cancelled`, `internal-error`.

### Capabilities

`getCapabilities()` → `{version, platform, overlay, overlayExcludedFromCapture, overlayFollowsWindow, globalKeys, globalKeysBackend, globalKeysReason?, keyCapture, globalKeysPermission, shortcuts, tray, screenSharePicker?}`

| field | meaning |
|---|---|
| `overlay` | the share border can be shown (`false` on Linux Wayland since 1.2.0, see `screenSharePicker`) |
| `overlayExcludedFromCapture` | `true` on Windows/macOS: the border is excluded from screen capture (`setContentProtection`). `false` on Linux: the border may be visible in the shared stream |
| `overlayFollowsWindow` | `true`: a shared *window* is followed (move/resize/minimize/close). `false`: a window share falls back to framing the primary display |
| `globalKeys` | push-to-talk is possible: native hook (`uiohook`) or, on Wayland, the desktop portal (`portal`) |
| `globalKeysBackend` | `'uiohook'` (Windows, macOS, X11), `'portal'` (Wayland, see [wayland.md](wayland.md)) or `null` |
| `globalKeysReason` | why `globalKeys` is `false`: `no-display`, `permission-denied`, `native-module-failed`, on Wayland `wayland-no-portal` / `wayland-no-global-shortcuts` |
| `keyCapture` | `captureNextKey` works (`uiohook` only; `false` on the portal backend) |
| `globalKeysPermission` | macOS Accessibility: `granted` / `denied`; `not-required` on Windows/Linux |
| `shortcuts` | `registerShortcut` available (Electron `globalShortcut`; on Wayland through the portal, `false` there without one) |
| `tray` | a tray icon exists, so `setVoiceStatus` has something to show it on |
| `screenSharePicker` | (1.2.0+, absent before: treat as `app`) how to capture the screen. `app`: list sources with `getDesktopSources()` and capture the id with `getUserMedia({chromeMediaSource: 'desktop'})`. `system` (Linux Wayland): the compositor's picker is the only picker; call `navigator.mediaDevices.getDisplayMedia()` and do not reconfigure the track ([Screen sharing on Wayland](wayland.md#screen-sharing-on-wayland-one-picker)) |

### Screen-share border

```ts
showShareBorder({sourceId, color?, thickness?}): Promise<{ok: true, target: 'window' | 'display'} | Failure>
hideShareBorder(): Promise<Result>
onShareBorderLost(listener: () => void): () => void   // the shared window was closed
```

- Not on Linux Wayland (`overlay: false`, the call returns `unsupported`): verifying the source would open the system picker again, and the frame could neither be placed nor kept on top there ([why](wayland.md#share-border-overlay-on-wayland)).
- `sourceId` is the `desktopCapturer` id the plugin already has: `screen:…` or `window:…`. It is verified against a fresh
  `desktopCapturer.getSources()` listing; unknown ids → `source-not-found`.
- `color`: `#rgb`, `#rrggbb`, `#rrggbbaa`, `rgb()`/`rgba()` (default `#e5252a`). `thickness`: integer 1-12 DIP (default 3).
- One border at a time (a new call replaces the old one). `showShareBorder` is rate limited (5/s per view, extra calls get `rate-limited`); `hideShareBorder` never is, and a hide always wins over a still-resolving show.
- The frame window is transparent, frameless, non-focusable, click-through (`setIgnoreMouseEvents(true, {forward: true})`), always on top
  (`screen-saver` level, visible over fullscreen spaces on macOS), loads only an inline page, sandboxed, no preload, no devtools.
- Window bounds are polled every 120 ms from the OS: Windows `user32`/`dwmapi` (extended frame bounds), macOS CoreGraphics,
  Linux X11 `libxcb`; all through `koffi` FFI. If bounds cannot be read (Wayland, FFI failure) the primary display is framed
  (`target: 'display'`). If reads keep failing while following, the frame switches to the display the window was last on.

### Global keys

```ts
registerPushToTalk({key, modifiers?}): Promise<{ok: true, backend, trigger?, requestedTrigger?} | Failure>   // one binding per view; re-registering replaces it
unregisterPushToTalk(): Promise<Result>
onPttDown(listener): () => void
onPttUp(listener): () => void
captureNextKey({timeoutMs?}): Promise<{ok: true, captured: {key, modifiers, type: 'keyboard' | 'mouse'}} | Failure>   // not on Wayland
cancelCaptureKey(): Promise<Result>
openAccessibilitySettings(): Promise<Result>                // macOS: prompts + opens Privacy & Security > Accessibility
openShortcutSettings(): Promise<Result>                     // Wayland portal: opens the system's shortcut settings for this app
onShortcutTriggerChanged(listener: ({id, trigger}) => void): () => void   // Wayland portal: the user changed/cleared a key
```

- `key` is a `KeyboardEvent.code` name (`Space`, `KeyV`, `F13`, `ControlRight`, `Backquote`, `Numpad0`, …) or a mouse button:
  `Mouse3` (middle, alias `MouseMiddle`), `Mouse4` (back, `MouseBack`), `Mouse5` (forward, `MouseForward`).
  Left/right mouse buttons are never bindable. (Wayland portal: mouse buttons cannot be requested, see [wayland.md](wayland.md#mouse-buttons).) `modifiers`: any of `ctrl`, `alt`, `shift`, `meta` that must be held on key-down.
- `onPttDown` fires once per press (auto-repeat is ignored); `onPttUp` on release, also when the owner goes away while the key is held.
- Implementation (`globalKeysBackend: 'uiohook'`): [`uiohook-napi`](https://github.com/SnosMe/uiohook-napi) (MIT, N-API prebuilds for win32 x64/arm64, darwin x64/arm64,
  linux x64/arm64). The hook only runs while a binding or a capture exists. Keys are **observed, not swallowed**.
- **Wayland** (`globalKeysBackend: 'portal'`): the key assignment belongs to the compositor (xdg-desktop-portal `GlobalShortcuts`, KDE Plasma, GNOME 48+). The
  system may show a confirmation dialog, and the user may bind another key than the one requested, so the promise resolves with `trigger`, the description of the key
  that is *actually* bound (`Ctrl+Alt+P`) — show it in your UI (`onShortcutTriggerChanged` tells you about later changes, `openShortcutSettings()` opens the system UI to change it).
  `captureNextKey` returns `unsupported-on-wayland`: do not offer a "press a key" capture there; register a default and show the result. Details, app id, compositor matrix: **[wayland.md](wayland.md)**; hand test: [wayland-ptt-test.md](wayland-ptt-test.md).
- `captureNextKey` resolves with the next key/mouse button pressed anywhere (for "press the key you want" in settings UIs). A lone
  modifier is resolved on release, so chords (`Ctrl`+`Space`) can be entered. Left/right clicks are ignored (so clicking the "set key" button
  is not captured). Only one capture at a time, default timeout 8 s (max 30 s), and the calling page must be focused.

```ts
registerShortcut({id, accelerator}): Promise<Result>
unregisterShortcut(id): Promise<Result>
onShortcut(listener: (id: string) => void): () => void
```

- On Wayland toggles go through the same portal session as push-to-talk (`registerShortcut` resolves with the bound `trigger`; `Activated` → `onShortcut`). Shortcut ids must stay stable (the compositor remembers keys per id); `ptt` is reserved.
- `accelerator` is an Electron accelerator (`CommandOrControl+Shift+M`). Safety rules: a plain key needs Ctrl/Alt/Cmd/Super, except F-keys and
  media keys (otherwise the shortcut would swallow normal typing system-wide); common editing/system combos (`Ctrl+C/V/X/A/Z/Y/S/W/Q`,
  `Alt+F4`, `Alt+Tab`, …) are rejected. Max 16 per view; an accelerator held by another view or app → `in-use`.

### Tray status

```ts
setVoiceStatus({connected, muted?, deafened?, live?, roomName?, labels?}): Promise<Result>
onTrayAction(listener: (action: 'toggleMute' | 'toggleDeafen' | 'stopSharing' | 'leave') => void): () => void
```

While `connected` the existing tray icon gets a colored badge (green connected, amber muted, red live, dark red deafened), the tooltip
shows `<room> (live, muted)` and the tray menu gets **Mute/Unmute, Deafen/Undeafen, Stop sharing (only while live), Leave** on top.
`labels` (`mute`, `unmute`, `deafen`, `undeafen`, `stopSharing`, `leave`; ≤ 40 chars) lets the plugin supply localized menu text.
`connected: false` clears everything. No second tray icon is created: when the user disabled the tray icon, `tray` is `false` and
`setVoiceStatus` returns `unsupported`.

## Plugin example

```ts
import type {BufyAPI, BufyWindow} from './desktop-api-bufy';

const bufy: BufyAPI | undefined = (window as BufyWindow).desktopAPI?.bufy;

async function setUpDesktopExtras(sourceIdFromCapturer: string) {
    if (!bufy) {
        return; // stock app / browser: nothing to do
    }
    const caps = await bufy.getCapabilities();

    // 1. border while sharing
    if (caps.overlay) {
        await bufy.showShareBorder({sourceId: sourceIdFromCapturer});
        bufy.onShareBorderLost(() => stopSharing());
    }

    // 2. push-to-talk (key from your settings; Mouse4 = side button on Windows/macOS/X11)
    if (caps.globalKeys) {
        bufy.onPttDown(() => mic.unmute());
        bufy.onPttUp(() => mic.mute());
        const r = await bufy.registerPushToTalk({key: settings.pttKey ?? 'F13'});
        if (r.ok && r.backend === 'portal') {
            // Wayland: the compositor decides the key; show what it bound and let the user change it there
            showHint(`PTT: bound by the system to ${r.trigger}`, () => bufy.openShortcutSettings());
            bufy.onShortcutTriggerChanged(({id, trigger}) => id === 'ptt' && showHint(`PTT: ${trigger || 'not bound'}`));
        }
        // settings UI: only offer "press the key you want" when caps.keyCapture (never on Wayland)
    } else if (caps.globalKeysPermission === 'denied') {
        showHint('Grant Accessibility access', () => bufy.openAccessibilitySettings());
    } // else: caps.globalKeysReason (e.g. 'wayland-no-portal') -> fall back to in-window key handling

    // 3. global toggles
    await bufy.registerShortcut({id: 'toggle-mute', accelerator: 'CommandOrControl+Shift+M'});
    bufy.onShortcut((id) => id === 'toggle-mute' && toggleMute());

    // 4. tray
    await bufy.setVoiceStatus({connected: true, muted: true, roomName: 'Lobby'});
    bufy.onTrayAction((a) => a === 'leave' && leaveRoom());
}

// on leaving: await bufy?.hideShareBorder(); await bufy?.unregisterPushToTalk();
//             await bufy?.setVoiceStatus({connected: false});
```

Registrations are per page: reload/navigation, a crashed renderer, closing the view/server or quitting the app removes them
automatically, so there is nothing to clean up after a crash.

## Security model

- **Who may call**: only the main frame of a Mattermost server view (tab or popout) or the Calls widget window, and only while it shows a page of
  the origin (scheme + host + port) of its configured server. Everything else (sub-frames, other origins, internal `mattermost-desktop://`
  pages, unknown webContents) gets `untrusted-sender` and has no side effect (`src/main/bufy/security.ts`). This is the same boundary
  upstream's `desktopAPI` relies on (the externalAPI preload is only attached to those views), made explicit because these calls change OS-level state.
  It does **not** distinguish between plugins on the same server: any script running in a trusted page can call the API, as with the rest of `desktopAPI`.
- **Validation**: every argument is validated with Joi (strict patterns for source ids/colors/ids/accelerators, numeric ranges, string lengths,
  unknown properties stripped). The overlay page is built from validated values only and has a CSP of `default-src 'none'`.
- **No arbitrary window control**: pages never get a handle to a `BrowserWindow`; the only window created is the fixed share-border frame.
- **Rate limits**: `showShareBorder` 5/s and voice status 10/s per view; shortcuts 16 per view; one capture at a time with a timeout.
- **Ownership & cleanup**: push-to-talk binding, shortcuts, share border, tray status and key capture belong to one `webContents`; events are
  sent only to it. They are released on `destroyed`, `render-process-gone`, main-frame cross-document navigation, `view-removed`
  (server/view removal) and app `will-quit`. A held PTT key is released (`pttUp`) first so a mic is never left open.
- **Keylogging surface**: a trusted page can learn press/release of *one* key it registered, or the *next single* key through a focused
  `captureNextKey`. It cannot observe other keystrokes. The hook is not running without a binding/capture.

## Platform notes

| | Windows | macOS | Linux X11 | Linux Wayland |
|---|---|---|---|---|
| screen share picker | own source list (`getDesktopSources`) | own source list | own source list | **the system's portal picker, once** (`screenSharePicker: 'system'`, `getDisplayMedia`) |
| border follows window | yes (user32/dwmapi) | implemented (CoreGraphics), **not yet verified on hardware** | yes (libxcb), verified under Xvfb | no border (`overlay: false`) |
| border hidden from capture | yes, Win10 2004+ (`WDA_EXCLUDEFROMCAPTURE`) | `NSWindowSharingNone`; **ScreenCaptureKit-based capture ignores it** on newer macOS, so the border may be visible in the stream | no (visible in a full-screen share) | no |
| push-to-talk | yes. Not seen while an elevated (admin) window has focus | needs **Accessibility** permission | yes (XRecord) | **yes via xdg-desktop-portal** (`globalKeysBackend: 'portal'`): KDE Plasma 5.27+/6 (tested 6.8), GNOME 48+; the compositor assigns the key, may show a dialog once; elsewhere `globalKeys:false` |
| `captureNextKey` | yes | yes | yes | **no** (`unsupported-on-wayland`) |
| global shortcuts | yes | yes | yes (X11) | via the same portal session (`registerShortcut` resolves with the bound `trigger`) |
| tray status | yes | menu bar item | needs StatusNotifier/AppIndicator support | same |

- **Exclusive fullscreen** (games, some video players): an always-on-top frame cannot be drawn over it; borderless-fullscreen is fine.
- **Wayland**: no protocol allows a global key hook (XWayland only sees events for X11 windows), so push-to-talk and shortcuts use the
  xdg-desktop-portal GlobalShortcuts interface instead ([wayland.md](wayland.md): backend selection, what the user sees, app id, compositor support).
  Without that portal `globalKeys` is `false` with reason `wayland-no-portal` / `wayland-no-global-shortcuts`; plugins fall back to in-window keys.
  Screen sharing shows the compositor's picker exactly once (`getDisplayMedia` with a placeholder source, [details](wayland.md#screen-sharing-on-wayland-one-picker)); there is no share border (`overlay: false`, [why](wayland.md#share-border-overlay-on-wayland)).
- **macOS Accessibility**: `globalKeysPermission` is `denied` until granted in System Settings › Privacy & Security › Accessibility.
  `openAccessibilitySettings()` triggers the prompt and opens the pane. Screen Recording (for sharing) is requested by the existing Calls flow.
- Border bounds on bare X11 (no window manager) are reported by Chromium 1 px smaller than the display; harmless.

## Branding

The app, tray and menu bar icons and the in-app logo are the **planet-mining** branding (our game), not Mattermost's. `productName`, `appId`
and the server web content are unchanged (see "Naming / coexistence").

- **Sources:** `planet-mining/assets/branding/` in the game repo (`icon.svg` app icon, `mark.svg` symbol, `logo.html` lockup; its README says how to render them).
- **Raster assets** in `src/assets/` keep upstream's file names, sizes and formats and are regenerated with
  `scripts/bufy-branding/generate.sh [path to planet-mining/assets/branding]` (headless Chrome + ImageMagick; default path is `../planet-mining/assets/branding`
  next to the repo checkout). It renders `icon.svg` with a transparent background into `icon.ico`, `icon.icns` (PNG-based, `icns.py`), `linux/app_icon.png`,
  `appicon_48.png`, `appicon_with_spacing_32.png` and `thumbnails/mattermost.svg` (the app-update thumbnail), plus `osx/DMG_BG.png` from `dmg_bg.svg`.
- **Tray / menu bar icons** (`linux/top_bar_*`, `windows/tray_*.ico`, `osx/menuIcons/*Template*`) are a monochrome silhouette drawn on a 32 px grid
  in `tray.py`: the planet with a 90° wedge cut from the top and the station hanging on its tether. Upstream conventions are kept: Linux dark `#323130` / light white,
  Windows dark black 70 % / light white 90 %, mention = red `#FF3B30` badge, unread = blue `#579EFF` dot (bottom right, with a transparent gap),
  macOS Template images black + alpha with a black unread dot. `tray.py` also writes the vector sources `resources/windows/tray*.svg`.
- **In-app:** `Images/PlanetMark.tsx` is a simplified colour mark (coordinates from `mark.svg`); `Images/Logo.tsx` is the header lockup (mark + "PLANET MINING",
  Russo One glyphs converted to paths, no web font). The loading screen (`LoadingAnimation`) shows the mark with an intro, a pulsing core and a dropping station.

### Updates

Upstream has no auto-installer, only an *update notifier* (checks `releases.mattermost.com`, shows a "new version" prompt and a link to the
stock download). It is disabled for this fork (`enableUpdateNotifications: false` → no "Check for updates" and no notification), so
nothing can point users back to the stock app. Updating = install a newer build of this fork.

### Naming / coexistence

`productName` (`Mattermost`), `appId` (`Mattermost.Desktop`) and therefore the **data directory** are unchanged: the fork **replaces the stock app in place**
and keeps servers, login sessions and settings. Coexisting with the stock app would mean a second data dir (re-login, re-add servers), a
second tray icon/protocol handler and a different Windows `AppUserModelId` (which upstream's Focus-Assist check depends on) for no real gain.
Consequences: only one of the two can run at a time (single-instance lock); the `mattermost://` protocol goes to whichever started last.
Packages are named `mattermost-desktop-bufy-…`; the deb/rpm package is called `mattermost-desktop-bufy` and declares
`Conflicts/Replaces/Provides: mattermost-desktop`, so installing it removes the stock package and `apt upgrade` does not bring it back.
The app version is deliberately left at `6.4.0` (the web app gates features on the desktop version in the user agent).

## Rebasing onto a new upstream release

```bash
git fetch upstream --tags
git rebase --onto vX.Y.Z v6.4.0 bufy/main      # or: git merge vX.Y.Z
git grep -n "\[bufy\]"                          # every hook in upstream files
```

Things to re-check after a rebase:
1. The hooks in the table above still apply (the tray and `externalAPI.ts` files change most often).
2. `package.json` Electron version vs. what `uiohook-napi` and `koffi` support (N-API → normally unaffected).
3. `patches/uiohook-napi+*.patch` still matches the installed version if `uiohook-napi` is bumped (`npx patch-package uiohook-napi` to regenerate).
4. `docker/Dockerfile` base image: upstream may raise the required Node version (`engines`, `.nvmrc`).
5. `npm run check` and `npx jest src/main/bufy`, then `xvfb-run -a node scripts/bufy-smoke.js` (needs `npm run build` first).
6. Re-run `node scripts/bufy-gen-types.js` if `shared.ts` changed.

Risk ranking: `tray.ts`/`menus/tray.ts` (upstream refactors of the tray) > `externalAPI.ts` (new API additions are additive, conflicts are one line) >
`initialize.ts` > the rest. `desktopAPI` types are not touched (the bufy API is attached outside the `DesktopAPI` interface, so `api-types/` stays identical).

## Tests

- Unit: `npx jest src/main/bufy` (15 suites: Wayland screen-share handler, keys, validation, trust resolution, global keys incl. permission gating, shortcuts, backend selection, Wayland portal session flow with a mocked D-Bus, trigger mapping, desktop entry, overlay geometry/following,
  overlay window flags, tray status, manager event routing/cleanup/rate limits). The upstream suite (`npx jest`) still passes.
- Live smoke test (Linux/X11, headless): `npm run build && xvfb-run -a -s "-screen 0 1920x1080x24" node scripts/bufy-smoke.js`.
  Starts the built app against a fake local server, drives `desktopAPI.bufy` from the page via the DevTools protocol, injects real
  keyboard/mouse events through XTEST, and checks window flags, bounds following, event delivery and cleanup.
